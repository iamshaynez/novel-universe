# 悬疑故事宇宙 · 工程架构提案 v0

> 目标：人物、地点、核心时间线全宇宙共享，每部作品故事独立；脚手架、素材、剧本、
> 游戏主干有序组织，且**加一部新游戏的开销趋近于"新增一个目录"**。
> 延续主仓库哲学：零依赖 Node 原生 ESM + `node:test`、内容即数据、内核纯函数、确定性。

## 0. 一句话架构

**Monorepo 四层：引擎（与宇宙无关）← 正典 canon（宇宙共享数据）← 素材（组件与配方）← 游戏（剧本+配置），外加一条工具链把剧本编译成引擎 IR 并全程 lint。**

依赖方向强制单向：`games → {assets, universe, engine}`；`engine` 不认识任何具体游戏与宇宙内容。

```
novel-universe/
├─ docs/                      # 本文档 + ADR
├─ engine/                    # 纯 VN 运行时（无 DOM、无 I/O，可 node:test）
│  ├─ state.mjs               # 状态机：IR + 选择序列 → 演出状态（纯函数）
│  └─ presenter.mjs           # 薄渲染层：SVG 组件合成 + Web Audio 挂载
├─ universe/                  # ★ 正典：宇宙的单一事实源
│  ├─ canon.json              # 纪元元数据、版本号
│  ├─ characters/*.json       # 人物档案（公开层/机密层、形象组件、声线参数）
│  ├─ locations/*.json        # 地点（场景配方引用、情绪色板、关联 BGM）
│  ├─ timeline.json           # 核心事件轴（宇宙内日期 + 披露作品 + 依赖）
│  └─ tokens.json             # 风格令牌：描边色/瞳色/调色板（风格圣经即代码）
├─ assets/
│  ├─ chibi/                  # 人物组件库（05/06 测试已验证的格式：SVG 片段 + 堆叠序）
│  ├─ scenes/                 # 场景配方（渐变+几何+参数化时间/天气，01/02/05 已验证）
│  └─ scores/*.mjs            # BGM 乐谱（种子+参数；07 已验证浏览器/离线双渲染）
├─ games/
│  ├─ g00-demo/               # 垂直切片（教程兼模板）
│  └─ g01-xxx/
│  └─ gNN-xxx/                # 每作一个目录，结构完全一致
├─ tools/
│  ├─ compile-scenario.mjs    # 剧本 DSL → IR JSON（确定性，可快照测试）
│  ├─ canon-lint.mjs          # 引用解析 + 剧透纪元 + 资源存在性校验
│  ├─ graph-test.mjs          # 分支图：入口唯一/结局全可达/无孤儿节点
│  ├─ new-game.mjs            # 脚手架：按模板生成 gNN 目录 + 红测试
│  ├─ build.mjs               # 组装 dist/gNN 静态站点（零依赖可部署）
│  ├─ build-wiki.mjs          # canon JSON → 人类可读设定集 HTML
│  └─ render-bgm.mjs          # （已有）乐谱 → WAV
└─ test/                      # engine 单测 + 全宇宙一致性测试
```

## 1. 正典 canon：宇宙的单一事实源

universe/ 下的 JSON 就是设定集本身（不是从文档抄来的第二份）。`build-wiki` 把它渲染成
可读 HTML 供人查阅，机器读 JSON——**永远只有一个源**。

### 1.1 关键机制：剧透纪元（spoiler epoch）

共享宇宙最大的工程风险是"后作剧透前作/引用不存在的设定"。解法是给每条正典数据打
披露标记，给每部游戏声明知识边界，lint 强制执行：

```jsonc
// universe/characters/momo.json
{
  "id": "momo", "name": "小桃",
  "first_appearance": "g01",
  "chibi": { "parts": ["hairBackA", "headA", "outfitA"], "iris": "#4a7fc9", "voice_hz": 205 },
  "bio_public":  "二年级，放学后总在天台……",
  "bio_secret":  [{ "fact": "她目击了那晚的事", "revealed_in": "g02" }],
  "timeline_refs": ["ev-2019spring-rooftop"]
}
```

```jsonc
// games/g02/game.json
{ "id": "g02", "assumes": ["g01"], ... }   // 玩家被假定玩过 g01
```

lint 规则：剧本中 `@show momo` 要求 `first_appearance ∈ assumes ∪ {本作}`；
`@fact` 引用要求 `revealed_in ∈ assumes ∪ {本作}`；`@location` 同理。
**前向引用直接编译失败**。加新游戏永不触碰旧作；旧作完结归档时把 timeline 事件
标记 `disclosed_in`，即自动对后续作品解锁。

> v0 采用严格线性披露（g01 → g02 → …）。若将来需要平行世界线/外传，把 `assumes`
> 从"有序前缀"升级为"知识集合"即可，数据结构不用改。

### 1.2 版本与兼容

- canon 整体一个 semver：新增条目/新增字段 = minor；改含义/删条目 = major。
- 游戏 `game.json` 声明 `canon: ">=2.1 <3"`。canon 破坏性变更 → 所有游戏 lint 变红，
  影响面一目了然。
- 素材同理：组件 id 稳定则各作自动继承修正后的画风；换 id 才算破坏性变更。

## 2. 剧本格式：给人（和 LLM）写的 DSL，给引擎吃的 IR

剧本是海量的散文，JSON 写作体验是灾难。采用 **Markdown 场景文件 + 极小指令集**，
编译成确定性的 IR JSON（机器合同），引擎只认 IR。

```md
# scene rooftop-dusk
@bg rooftop time=dusk
@show momo neutral
@bgm rooftop

小桃：「今天的风，好像有点温柔呢。」
她把发梢别到耳后，没有看我。

* 我今天，必须问出那件事。     -> ch1-ask
* 再让她安静一会儿吧。          -> ch1-wait
```

- 指令只有 6 个起步：`@bg @show @hide @bgm @sfx @fact`；台词即正文；`*` 为选项。
- 分支、flag、好感度都编译成同一个 DAG + 状态方程，引擎不解析 Markdown。
- 编译是纯函数：同输入同输出 → IR 走快照测试，剧本 diff 在 PR 里人类可读。
- 状态模型刻意收窄：**布尔/整数 flag + 种子 RNG**，不给图灵完备脚本（防失控，也保确定性）。
  存档 = `{gameId, 版本, 选择向量, seed}`，天然可回放、可 e2e。

## 3. 引擎与素材：已验证的三块拼图直接转正

- **engine/state.mjs**：`(IR, 选择序列, seed) → 演出状态`，纯函数、`node:test` 直测。
  presenter 是薄壳：按演出状态拼 SVG 组件、挂 Web Audio。e2e 不需要真浏览器——
  引擎层回放即测试；渲染层用 golden 截图抽查（沿用本次无头 Chrome 方案）。
- **assets/chibi**：人物 = SVG 片段组件 + 堆叠序 + CSS 变量（瞳色/服装换色），
  即 06 号测试的格式。新增角色 = 一套 parts + 一行 canon 登记。
- **assets/scenes**：场景配方 = 渐变 + 几何 + 参数（时间/天气/镜头），即 01/02/05 的格式。
  "黄昏天台"换 `time=night` 即派生新场景，不重画。
- **assets/scores**：BGM = 种子 + 参数的乐谱模块，浏览器实时合成（07 demo）或
  构建期离线渲染 WAV（render-bgm.mjs，MD5 已验证确定性）。台词音效声线参数
  挂在角色档案的 `voice_hz` 上。

## 4. 单部游戏的开发流程（工程管理）

脚手架统一，节奏分四个门：

1. **立项**：`node tools/new-game.mjs 雨夜来信` → 生成 `games/g01-雨夜来信/`
   （manifest + 样章 + 全红测试）。附一页立项文档：题材、案情设计、
   **本作需要新增/披露哪些 canon 条目**（canon 变更走独立 PR，与游戏 PR 分离评审）。
2. **写作期**：章节按 PR 增量合入。每个 PR 的合并门 =
   `编译通过 + canon-lint + 分支图测试 + 字数/覆盖率报告`（对标主仓库"三合一评审"：
   设计 diff = 立项文档/canon，代码 diff = 引擎/工具，测试 diff = 场景断言）。
3. **里程碑**：`v0`（第一章可玩）→ `alpha`（全分支闭合、结局全可达）→
   `rc`（BGM/演出/音效打磨）→ `g01-v1.0.0` tag 发布 dist。
4. **归档**：完结后游戏目录冻结（只接受翻译/bugfix），canon 打上本作披露标记，
   宇宙资产沉淀给下一作。

分支管理沿用主仓库习惯的轻量版：`main` 保护 + `feat/*` 短命分支 + PR；
每作发布打 tag。单人 + AI 协作下不需要长期并行分支。

## 5. 测试策略（TDD 落点）

| 层 | 测试 | 性质 |
|---|---|---|
| 引擎 | 状态机单测：选择序列 → 结局/flag 断言 | node:test |
| 编译器 | 剧本 → IR 快照；非法指令/循环跳转报错 | node:test |
| 剧本 | 分支图：入口唯一、结局全可达、无孤儿节点、选项目标存在 | 属性测试 |
| 正典 | 引用解析、纪元合规、资产 id 存在、时间线无环 | lint（CI 门） |
| 素材 | BGM 离线渲染 MD5 不变；场景配方渲染 golden 截图 | 确定性断言 |
| 整体 | 引擎回放全结局（无浏览器）；audio 静默跑 | e2e |

## 6. 开放决策（需要拍板）

1. **g00-demo 的定位**：垂直切片直接做成 g00（保留为教程/模板），还是做完即弃？
   建议保留——它永远是脚手架的活样板。
2. **纪元模型**：v0 严格线性披露（推荐，简单）；平行世界线需求出现后再升级知识集合。
3. **剧本 DSL 确认**：Markdown + 6 指令（推荐）；若你更想要纯 JSON 也可以，
   IR 合同不变，只是写作体验取舍。
4. **第一部正作的题材与规模**：建议第一部控制在 3–5 章、2–3 结局，
   先把整条流水线跑热再上体量。

## 7. 扩展能力总账

- 加一部新游戏 = 新目录 + 声明 assumes，零改动旧作。
- 加角色/地点 = canon 增量 + 素材包，全宇宙可选引用，lint 保证不被提前剧透。
- 引擎升级 = IR 合同不变，全部旧作重新 build 即受益。
- 素材升级 = 组件 id 不变即全作自动继承（画风统一性由 tokens.json 兜底）。
- 宇宙变大后的查询 = build-wiki 生成的设定集 + timeline 可视化。
